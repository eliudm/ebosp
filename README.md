# EBOSP — Enterprise Business Operations & Security Platform

A production-style, modular business application combining operational workflows (inventory, procurement, sales, invoicing, payments) with security, auditability, reporting, real-time notifications, anomaly detection, document management and an optional read-only AI assistant.

**Stack:** C# / ASP.NET Core · React / TypeScript · PostgreSQL or SQL Server · Azure · Docker · CI/CD
**Architecture:** Modular monolith + asynchronous domain events (Outbox pattern) + REST API + relational database. See [ADR-0001](docs/decisions/0001-modular-monolith-first.md).

## Build order (do not skip ahead)

Per dev guide §4, modules are built in dependency order — each phase assumes the previous one is done and tested:

`0` Requirements/architecture (this prep) → `1` Repo/CI/DB foundation → `2` Identity & tenant → `3` Master data (branches/warehouses/products) → `4` Inventory ledger → `5` Procurement + approvals → `6` Sales + fulfillment → `7` Billing + payments → `8` Audit + security analytics → `9` Notifications + documents → `10` Reporting → `11` AI assistant (read-only) → `12` Hardening → `13` Azure deployment → `14` Handover.

Production Dockerfiles for the API and Worker are done (`infra/docker/api.Dockerfile`, `worker.Dockerfile`) — multi-stage, non-root, runtime-injected config, container health checks — verified by building and running both images against the local Postgres container, and by a clean Trivy scan (0 vulnerabilities after pinning `apk upgrade` in the runtime stage).

**Hardening pass on M2 before M3 started:** an independent, confidence-filtered multi-agent security review of the full Identity diff found and fixed two real issues — a login timing side-channel (password hashing now always runs, even on the fast-fail paths) and account-existence enumeration via the tenant/user-creation conflict responses (now generic, plus refresh-token reuse now revokes the whole session family as a theft signal). Separately: the rate limiters were global rather than per-client (one burst of traffic could've locked out every user), now partitioned per IP with configurable limits and a proper 429 response; added HSTS and baseline security headers (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`). 33/33 tests green (backend + the new rate-limiting coverage), 0 vulnerable packages, format/build clean in Release.

**Phase 4 (Inventory ledger):** StockBalance (the fast-read projection), StockLedgerEntry (immutable, append-only history), GoodsReceipt/StockAdjustment/StockTransfer/StockReservation, and ReorderRule (per-warehouse override of `Product.ReorderLevel`), behind `InventoryController`/`ReorderRulesController`. Dev guide §13.2's rules are all real, not aspirational: negative stock is hard-blocked; receipts/adjustments/transfers carry an optional idempotency key with a unique index preventing double-processing; large adjustments (over a configurable threshold) need a second permission (`inventory.adjust.large`) in addition to `inventory.adjust`, checked imperatively since it depends on request content; `StockBalance` concurrency is enforced via Postgres's `xmin` system column as a real EF Core concurrency token, with a jittered-backoff retry loop in `InventoryService` — proven under ten genuinely concurrent HTTP requests hitting the same balance row, not just unit-tested in isolation. Low-stock detection fires once per threshold-crossing, not on every subsequent movement. Neither governing spec gives field-level detail for most of this module (confirmed by exhaustive search — StockReservation/StockTransfer/StockAdjustment/ReorderRule are named once each with no fields anywhere), so the design followed dev guide §13.1's entity list literally and filled the rest by judgment, documented in the M4 plan. 101/101 tests green, 0 vulnerable packages, format/build clean in Release.

**Hardening pass on M4:** an independent review specifically probed the new concurrency-retry and idempotency logic (the riskiest new territory this phase) and found two real bugs, both fixed: silent integer overflow in `StockBalance.Receive`/`AdjustBy` (unchecked arithmetic could wrap a corrupted-but-internally-consistent negative balance with no exception, then permanently block further movement on that line), and adjustment requests with `QuantityDelta = int.MinValue` or `0` falling through to an unexplained 500 instead of a clean 400. Everything else reviewed clean — tenant isolation, IDOR, the large-adjustment authorization check (confirmed unbypassable, including the theorized `Math.Abs` overflow path), idempotency-key scoping, and the retry loop's ledger/balance consistency under EF Core's transactional `SaveChanges`.

**Phase 5 (Procurement + approvals):** Supplier (vendor master), a generic `WorkflowInstance` (keyed by `EntityType`/`EntityId`, reusing the idiom `OutboxMessage` already established, rather than folding approval state into each approvable entity), PurchaseRequest/PurchaseOrder with line items, behind `SuppliersController`/`PurchaseRequestsController`/`PurchaseOrdersController`/`WorkflowsController`. Mirrors M4's two-tier permission pattern exactly: `procurement.approve` covers ordinary approvals, a new `procurement.approve.large` (granted to `tenant-admin` and `finance`) is additionally required above a configurable threshold, checked imperatively since it depends on the request's persisted estimated value, not its body. Self-approval is denied the same way M2's `UserService.SuspendAsync` denies self-suspension. Approving a request does not auto-create a purchase order (spec §8.3 says approved requests "can" generate one, not "must") — that's a separate action, guarded so a request can convert to at most one PO. `GoodsReceipt.PurchaseOrderId`, left nullable in M4 specifically for this phase, now validates the referenced PO belongs to the caller's tenant. Neither governing doc gives field-level detail here (no `PurchaseOrderLine` ERD row at all; §17's tiered-approval example is explicitly illustrative, not a mandated schema), so Supplier's module placement, the two-tier (not three-tier) approval, and PO creation being manual and idempotent were judgment calls, documented in the M5 plan. 126/126 tests green, 0 vulnerable packages, format/build clean in Release.

**Hardening pass on M5:** an independent review traced the two-tier `procurement.approve.large` check end-to-end (fetch tenant-scoped request first, so a cross-tenant id 404s before the threshold check can run; compare against the persisted, immutable `EstimatedValue`; only then the imperative `IAuthorizationService.AuthorizeAsync` call, `Forbid()` on failure, before `ApproveAsync` is ever invoked) and confirmed it's not a weaker code path than a static `[Authorize]` attribute - `PermissionPolicyProvider` resolves both identically. The self-approval guard compares against immutable, persisted data with no update path, so there's no race window on either side of the check. PO-creation's idempotency guard (approved + not-already-converted) runs in the correct order, both tenant-scoped, before any mutation. Migration/seed consistency confirmed - Manager holds only base `procurement.approve`, never the `.large` tier; Finance holds both (needed, since the controller's static policy attribute gates the action unconditionally before the `.large` check ever runs - a gap caught and fixed with its own migration before this review even started). No High/Medium findings; the one low-severity note (a crafted price near `decimal.MaxValue` could overflow the line-total multiplication into an unhandled 500) mirrors an existing, unfixed pattern already present in M3's `Product.UnitPrice` and was left as-is for consistency rather than diverging only for this module.

**Phase 6 (Sales + fulfillment):** Customer, `Quotation`/`SalesOrder`/`Delivery` with line items, behind `CustomersController`/`QuotationsController`/`SalesOrdersController`/`DeliveriesController`. Covers dev guide §15's flow through Delivery only — Invoice/Payment is the separate "Billing + payments" build step and stays a follow-up phase, so this does **not** yet close the milestone table's M5 "Order-to-cash" row. Unlike M5's `PurchaseOrder` (fresh lines, since procurement re-negotiates supplier pricing), a `SalesOrder`'s lines are copied verbatim from the `Quotation` the customer accepted — letting staff silently redefine them afterward would defeat the point of a quotation being a price commitment. `SalesOrderService` finally exercises `IInventoryService.ReserveAsync`/`ReleaseReservationAsync`, unused since M4 (`StockReservation`'s own doc comment predicted exactly this dependency); reserving stock per line reuses `InventoryService` as-is rather than reimplementing its hardened concurrency-retry logic against a second unit of work, with explicit release-on-partial-failure compensation if a later line's reservation fails partway through a multi-line order — proven by a test that deliberately fails on the second line and verifies the first line's reservation was released, not left orphaned. A new two-tier permission split (`sales.create` for quotations/orders, `sales.fulfill` — separate and stricter — for deliveries, since that's the action that actually moves physical stock) mirrors the `inventory.adjust`/`inventory.adjust.large` shape without the threshold, granted to a new `sales-officer` role matching spec's actors table. Credit-limit checking sums open `SalesOrder` totals per customer (there's no Invoice/Payment yet to know what's actually still owed — flagged as a simplification for Billing + payments to revisit). Neither governing doc gives this module full field-level detail (no ERD row for `Quotation` or `Delivery` at all, despite the flow naming both), so `Quotation` skipping `WorkflowInstance` (accepting one records the *customer's* decision, not an internal approval with a segregation-of-duties concern) and full-order-only delivery (no partial shipments) were judgment calls, documented in the M6 plan. 150/150 tests green, 0 vulnerable packages, format/build clean in Release.

**Hardening pass on M6:** an independent review found and fixed one real, concrete bug in the new reservation-compensation logic — the try/catch around `SalesOrderService.CreateAsync`'s stock reservations only wrapped the reservation loop itself, not the final `SaveChangesAsync` that persists the `SalesOrder`. Two concurrent requests converting the *same* quotation could both reserve stock successfully and then race on the `SalesOrder(TenantId, QuotationId)` unique index; the loser's already-committed reservations were left permanently orphaned (each `ReserveAsync` call commits independently, so they were durable even though the order they belonged to never got created), silently bleeding available inventory on every occurrence. Fixed by widening the try/catch to cover the whole save — which surfaced a second, subtler bug in the fix itself: a failed `SaveChangesAsync` leaves its entities tracked in their pending state on that request's scoped `DbContext`, so the compensating release calls were themselves failing the exact same way on retry. Added `IUnitOfWork.DiscardChanges()` (`ChangeTracker.Clear()`) to clear that state before compensating. Reproduced with a genuine two-concurrent-HTTP-request regression test (not just reasoned about) before and after the fix. Separately flagged, not fixed: the credit-limit check has a similar but narrower TOCTOU race across *different* quotations for the same customer — fixing it would mean introducing row-level locking, a pattern not used anywhere else in this codebase, for a business control neither governing doc requires be strictly serialized; documented explicitly in code as an accepted gap rather than silently left unmentioned. Confirmed clean elsewhere: tenant isolation, IDOR, the `sales.create`/`sales.fulfill` permission split, and that `SalesOrder` lines can't be tampered with via the API (the create request carries only a `QuotationId`, never `Lines`).

**Phase 3 (Master data):** Branch (extended from M2's minimal shell), Warehouse, ProductCategory and Product, each with full CRUD (`BranchesController`, `WarehousesController`, `ProductCategoriesController`, `ProductsController`) behind a new `master-data.manage` permission (granted to `tenant-admin`) — reads need only authentication, since catalog browsing is broadly needed across roles. SKU is unique per tenant (composite index); `Warehouse.BranchId` and `Product.CategoryId` are real DB-level FK constraints (`DeleteBehavior.Restrict`), validated server-side against the caller's own tenant before insert (404, not a raw DB error, on a cross-tenant reference — deliberately going further here than M2's `UserRole.BranchId`, which a security review flagged as unvalidated and was correctly left alone at the time since nothing consumed it; these FKs are actually consumed). Neither governing spec gives field-level detail for this module beyond `Branch(BranchId, TenantId, Name)`, `Warehouse(WarehouseId, BranchId)`, `Product(ProductId, SKU, Name, TaxCode, ReorderLevel)`, so several gaps were filled by judgment call (documented in the M3 plan): no product-category hierarchy, `UnitPrice`/`TaxRatePercent` in place of the spec's bare `TaxCode`, `ReorderLevel` as a scalar (the dev guide's own `ReorderRule` entity is bucketed under the later Inventory module). First real use of the Phase-1 `PagedRequest`/`PagedResult` pagination convention. 58/58 tests green, 0 vulnerable packages, format/build clean in Release.

**Phase 2 (Identity), backend complete:** Tenant/Branch/User/Permission/Role/UserRole/RefreshToken/PasswordResetToken domain entities (`src/EBOSP.Domain/Identity/`); EF Core migrations `AddIdentityModule` + `AddPasswordReset` with a seeded, fixed role/permission catalogue (spec §15); tenant isolation enforced as a single EF Core global query filter over every entity implementing `ITenantOwned` (spec §12), not left to each query author. Self-service tenant onboarding (`POST /api/v1/tenants`), login/refresh/logout with short-lived JWT access tokens plus revocable, rotating refresh tokens (`AuthController`), and user lifecycle + role assignment gated by policy-based RBAC (`UsersController`, permission-code policies via a dynamic `IAuthorizationPolicyProvider`). Failed logins lock the account after 10 attempts (spec §16) and rate-limit the login endpoint; identity events (`UserCreated`, `LoginFailed`, `UserSuspended`, etc.) feed the existing Outbox. Password reset/recovery (`/auth/password-reset/request` + `/confirm`) never reveals whether an account exists and revokes existing sessions on a successful reset - delivery itself is a log-only placeholder (`LoggingPasswordResetNotifier`) until the Notifications module exists. An MFA-ready seam (`IMfaChallengeProvider`) sits in the login flow, defaulting to a no-op until an org enables it (spec §11). URL path API versioning is live (`Asp.Versioning.*`, per ADR-0003). Dev guide §11.2's full authorization test matrix is covered by `EBOSP.ApiTests` against a real Postgres + real host; `EBOSP.IntegrationTests` proves the tenant query filter actually excludes cross-tenant rows.

## Development discipline (non-negotiable, dev guide §1)

- Do not build screens before domain rules, entities, workflows, API contracts and acceptance criteria.
- Do not trust the frontend for security — every authorization/validation rule is enforced server-side.
- Do not mutate stock, payments or other high-value state through ad-hoc updates — only explicit, audited business commands.
- Do not publish an event before its DB transaction is committed — use the Outbox pattern.
- A feature is not "done" until it satisfies the full [Definition of Done](docs/source-specs/02-development-guide.md#2-definition-of-done--mandatory-for-every-feature) (requirement, design, backend, database, frontend, events, audit, security, tests, observability, docs, review, deployment, acceptance).
